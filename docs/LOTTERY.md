# Mini App 群抽奖

抽奖使用现有 `/app` 与 `/api/app/lottery/*`，不另开后台域名、不新增 Bot polling 或 Cron。页面采用与会员面板一致的设计语言并自适应 Telegram 深浅色模式：背景彩色光斑、蓝紫渐变白字按钮、毛玻璃质感卡片、原始彩色 LUCKY 字母与节日礼物素材，结合活动倒计时与节日庆祝感视觉；没有演示身份、演示名单或固定中奖结果。

## 配置与入口

1. 保留 [MINIAPP.md](MINIAPP.md) 的 HTTPS 与反向代理边界，只公开 `/app`、`/app/*`、`/api/app/*`；不要公开管理后台路由。
2. 配置并启用 Bot、会员面板地址和「群互动白名单」。把 Bot 加入目标群并设为管理员，确保 `getChatMember` 能可靠检查其他用户；禁止发言等群权限仍需正确配置。
3. 在 **BotFather → Bot Settings → Configure Mini App → Enable Main Mini App**（客户端文案可能不同）设置该 Bot 的主 Mini App，地址与配置的会员面板地址对应。群里不能使用 `web_app` 按钮，本功能使用普通 URL：`https://t.me/<当前Bot用户名>?startapp=lottery_<活动ID>`。代码只从 `getMe` 获取用户名，不猜 short_name；发布时要求 `has_main_web_app=true`，否则拒绝发布。仅配置私聊 Web App 按钮不等于配置了 Main Mini App。
4. 管理员是**已绑定账号的现有 admin 角色**，通过 Telegram initData 验签后查库认定，不信任 URL、前端角色或客户端传入 uid。管理员会员首页显示「抽奖管理」；普通会员不显示该入口，未注册用户也无权访问管理 API。
5. 抽奖正文使用 Telegram 原生 `<tg-emoji emoji-id="…">…</tg-emoji>`，按钮使用 `icon_custom_emoji_id`。Bot 所有者需具备 Telegram 要求的 Premium 条件。素材来自指定的 Colorful Font、ZaiHuaNews、Mix Emoji，来源见静态素材目录的 `SOURCES.md`。本功能不会改动其他 Bot 文案/按钮。

## 管理员操作

- 管理员从群深链进入时与群友一样报名和领奖，额外有「管理本期」入口；从个人页「抽奖管理」进入活动则默认管理视图，可返回参与页。管理员不豁免报名条件、积分费用或风控。
- 抽奖管理 → 新建：填写标题、白名单群、可选话题 ID、参与对象、报名费用、开奖方式、北京时间截止时间，并添加奖项。话题 ID 仅用于论坛群；应由管理员确认目标话题实际存在且可发言。
- 新建/复制/主动保存的草稿，仅「已注册」对象可选**参与门槛**（0 / 空为不限）：`min_level` 最低等级 0–8（现有等级体系的 Lv 数字，等级体系未启用时不能设置）、`min_points` 最低积分余额 0–1000000（只校验不扣）、`min_watch_hours` 近 30 天观看时长 0–720 小时（与会员端「近 30 天」同一口径 `StatsService.watch_summary()['seconds_30d']`）。「全部群友」或「仅未注册」时，服务端把报名费用和上述三个门槛统一归零（即使旧表单仍提交隐藏值），不会继续收费或限制报名；仅已注册奖池不能包含本人注册资格奖。
- 每期开关 `reminder`（截止前提醒）与 `pin`（静默置顶）必须为布尔值；定时开奖的新建默认开启，手动/满员开奖服务端固定 `reminder: false`，`pin` 仍默认开启。中奖私信与报名人数实时更新不是草稿开关：升级后**发布**的活动在发布时冻结为开启（`winner_dm` / `live_count`），旧活动缺字段一律按关闭处理。
- 「复制上期」：任一活动（草稿/进行中/已开奖/已取消）的奖池、对象、费用、门槛、开关、群/话题、开奖方式复制为新草稿；截止时间清空（定时开奖须重新填写才能保存/发布，手动/满员开奖不设置时间，满员人数上限保留）；复制采用下述新业务版本，非会员对象的费用/门槛清零，奖池与对象不兼容则明确拒绝复制；商城奖品按当前商品重新校验（已下架则复制失败）；原群已不在白名单时群需重新选择。写审计 `lottery.copy`。
- 「删除草稿」仅限 `draft`，需显式 `confirm: true`，写审计 `lottery.delete`。已发布未开奖的活动只能「取消」：需 `confirm: true`；状态变为 `cancelled`，不再报名、不再开奖（含定时开奖）；收费活动按每人实际扣除的报名费全额退回积分（账本理由 `lottery.refund`，引用 `lottery.refund:<活动ID>:<TG ID>`，重复/并发取消不重复退）；群里回复原发起公告发简短取消通知，发起公告最后编辑为「活动已取消」，并取消置顶。已开奖不能取消；取消与开奖、报名共用同一数据库写锁，只有一方生效。写审计 `lottery.cancel`（含退款人数与积分）。
- 草稿可编辑（奖项可移除/重新添加）。保存时服务器验证对象、商品、分组、奖项数量与天数；同一草稿的并发编辑有 revision 冲突保护。
- **业务版本冻结**：服务端对新建、复制及管理员主动保存的草稿写入 `eligibility_version: 2`，客户端不能选择旧版。该版本独立于 `public_rules_version`，详情配置公开给 UI（缺字段读为 1，不回写）。旧未编辑草稿可按已存旧版直接发布；已发布/已开奖活动按冻结旧版保留手动截止、all 收费/门槛及 guest 账户奖规则。无数据库迁移、批量回填、退款或补抽。旧草稿保存升级业务版本时，仍保留服务器存量 `device_check` 和公开提示版本。
- 「发布前预览」只展示正文，不发送消息。确认发布后进行 Bot/主 Mini App/群身份检查，再冻结全部活动配置并持久化发起公告。发布结果中应查看**公告状态**，不能只看到活动是「报名中」就认为群消息已成功。
- 每期支持 1–20 个奖项、最多 200 个获奖名额；每项 1–200 名。积分每人 1–100000、可用邀请名额每人 1–100；注册资格有效天数 1–3650。截止时间须为保存/发布检查时至少一分钟之后、最多 366 天之后。定时开奖必须填写截止时间，到点自动开奖；所有已发布未结束活动（定时、手动、满员）均允许管理员提前手动开奖，权限与同一开奖事务不变；新业务版本的手动开奖固定 `deadline: null`，即使旧表单提交时间也会清空，开奖前一直可以报名，管理员开奖即截止，也不发截止前提醒。
- **满员开奖**：`draw_mode: "count"`，`max_entries` 必须为 1–100000 整数，拒绝 bool/小数/字符串。`manual/timed` 保存时将隐藏 `max_entries` 清零；`count/manual` 清空截止、关闭提醒。旧缺字段按 0 读取，不回填。详情公开 `count` 与 `config.max_entries`；进行中列表和管理员列表返回 `draw_mode/max_entries/count`，公开规则/预览/群公告显示「满X人自动开奖」。
- 满员判断采用公开成功报名总数，包含静默排除者；最后一份报名、扣费、关联记录、人数检查、开奖结果与公告/私信任务在同一 `BEGIN IMMEDIATE` 内原子提交，最后一名正常进入候选筛选。并发不超人数/超扣、不重抽；失败整笔回滚。发奖及外部发送在提交后走原维护任务，生命周期另兜底处理满员但尚未结算的记录；未满不会因时间过去自动开奖。取消、人工开奖与最后报名竞争同一终态锁。
- 每期默认开启「严格防小号」，草稿可关闭；新建及复制活动的环境校验已退役，服务端固定保存 `device_check: false`，不采集硬件环境、不据此排除或生成疑似列表。存量草稿按服务端已存 `device_check` 保留原策略，客户端不能重新开启或悄然关闭；缺字段视为 false（详见下文）。发布后连同奖池、参与对象、群/话题、人数、时间全部冻结，不提供临开奖放行或重抽。手动开奖可提前停止报名，需再次确认；定时开奖在截止后的现有 lifecycle 维护周期执行（默认周期 15 秒，繁忙时可能延后）。截止边界由服务器硬性判断，不依赖浏览器时间。
- 每期详情显示报名总数、异常排除人数和当前候选人数；「报名记录 / 关联异常账号」分页查看报名及结果，并查看关联簇的昵称、必要 TG ID、直接关联原因（IP / 浏览器标识；历史活动另有「设备环境特征相同」）、关联时间和排除结果。关联证据不返回 IP/设备原值或摘要。只有后端确认的管理员可以访问这些数据，普通端无法通过伪造角色获得。
- 已开奖页显示真实中奖名单、每份奖励的状态（管理员额外看到每份奖励的中奖私信结果 `dm`）、各条公告的独立状态，以及 `operations` 中提醒 / 置顶 / 取消置顶 / 报名人数更新 / 中奖私信汇总的状态与失败原因。人工奖品实际交付后再点「确认已人工发放」。发放记录与管理员操作进入 `audit_log`。

## 群友参与与领奖

- 从群按钮直达对应活动。initData 必须由 Telegram 签名，但不要求先注册/绑定。无活动深链的未绑定用户只看到欢迎/指引，不会取得会员私有数据；原会员 API 仍要求绑定。
- 会员首页「进行中的抽奖」：`GET /api/app/lottery/ongoing`（已注册/未注册均可，initData 验签）只返回已发布、未截止、未取消的活动摘要和本人是否已报名，不返回群 ID、风控或他人信息，不为列表调用 Telegram。若本地已有该 TG 在某些群报名过的记录（报名时已核验群成员），只列这些群的活动；没有本地依据时列出全部进行中活动，实际报名仍实时核验群成员。
- 设有参与门槛的活动，报名时按当时数据判定（等级、积分余额、近 30 天观看），不满足返回明确原因（如「需要 Lv3 及以上（当前 Lv2）」）。门槛是公开条件，写入公开规则和发起公告。
- **先私聊启动 Bot**：新建/复制/管理员主动保存草稿由服务端固定 `require_private_start: true`，客户端 false/legacy 标记无效；旧配置缺失按 false，旧未编辑草稿发布不升级，已发布/已有报名/中奖不追溯改变。详情返回 `bot_private_required`（启用且本人未报名）、`bot_private_ready`、`bot_private_reason`、`bot_start_url`；未知用户点击 `?start=lottery_<id>` 私聊启动后返回活动报名，未满足在同一写事务内扣费前拒绝。管理员也适用，已报名重复请求不再次要求启动或扣费。
- 私聊证据仅来自 Bot 收到的可信 private 消息/私聊成员事件，或同一 Bot ID 的旧成功私聊菜单消息 ID；不使用会员身份、getChat、群互动或客户端 bool 推断。新状态存于现有 `meta` 的 `telegram.private:<BotID>:<TGID>`，没有消息正文、凭据或新数据表；明确封禁事件及中奖私信不可达会覆盖旧菜单证据，较旧更新不覆盖较新状态。无历史证据者重新发送 `/start`，不伪造回填。用户报名后仍可能拉黑 Bot，门槛不保证 100% 送达，失败不撤销已有奖项。
- 报名时必须属于发布群，且符合全部/仅已注册/仅未注册的条件。查询失败、已离群或受限且非成员时拒绝报名；不会把查询失败当作已入群。
- 报名费用 `entry_fee` 为 0–100000 整数，0 免费；旧活动缺失该字段时仍免费，不回写旧配置或补扣。新业务版本仅「已注册」活动可收费，要求已绑定积分账户，不能配置本人注册资格奖；all/guest 保存时费用归零。历史已发布「全部群友」收费活动仍要求积分账户并按冻结费用执行。
- 收费按钮展示金额，确认后才提交 `expected_entry_fee`；后端要求与冻结费用相同，旧客户端未确认费用时拒绝收费。公告和页面明确成功报名后不退，未中奖或关联排除也不退款；唯一例外是管理员取消活动时全额退还。报名失败不扣费。
- 新建/复制活动的公开规则、发布预览及新群公告不再出现多账号检测提示或具体方法；保留参与资格、抽取规则、报名费用、成功报名不退及取消活动全额退款等必要说明。服务端在配置 JSON 写入 `public_rules_version: 2`；缺字段或版本 1 保留原公平声明策略，旧收费发起公告仍附同一句；已发布/已开奖活动的旧公开规则原文不变，旧草稿主动保存升级业务版本时只更新业务规则部分。编辑时从同一事务中的已存配置保留版本，客户端传版本/legacy 标记无效；复制始终取新版，发布保留该草稿版本。版本不返回普通端，无数据库迁移或批量回填，已冻结/已发出的旧公告不改写、不因此编辑或重发。
- 仅历史已开启设备环境校验的活动：页面先按详情中的 `consent` 显示「设备校验」说明，用户点「同意并报名」后才采集设备信息并提交；点「不同意」则不能参加这一场。未同意、同意版本不符或采集失败时拒绝报名且不扣费（详见「历史设备环境校验兼容」）。新建/复制及其他未开启的活动不返回 `consent`，不显示说明、不采集。
- 扣积分、报名与关联记录在同一事务完成；账本理由 `lottery.entry`，引用 `lottery.entry:<活动ID>:<TG ID>`。数据库唯一键保证每个 TG 每期仅一次，重复或并发请求不重复扣费、不增加名额。到达截止时刻即停止报名；已经报名者可刷新活动查看结果。
- 所有已接受的报名统一显示「报名已记录 / 等待开奖」。风控静默执行，普通响应不包含本人风险、排除、关联簇或有效候选人数；普通总报名数包含异常报名。结果页按真实结果正常显示未中奖，不伪造获奖或奖励发放。异常名单不会进入群公示。
- 奖项使用 `secrets.SystemRandom` 无偏抽样。**先抽本人注册资格，再抽其他奖项**；两个类别内奖项随机排序，每个名额在剩余合资格报名者中等概率抽取。每人最多一奖；人数不足如实少发，不补抽。
- 报名对象按报名当时账号状态判断。新业务版本的奖项按**开奖事务内的当前注册状态**隔离：`registration` 仅未注册；`points` / `invite` / `shop` 仅已注册（商城 custom 品同样依赖账户背包）；`manual` 通用，无需另选奖项身份。全部群友可混合奖池；member 含注册资格、guest 含任何账户奖时拒绝保存。不是使用报名时的 `registered` 快照；已报名后身份变化不撤销报名，按最新身份抽取适合奖项。
- 新详情 `config.prizes[].audience` 为服务端按类型派生的 `member/guest/all`（客户端不能覆盖），新公开规则和发起公告注明适用身份。详情的 `prize_eligible` / `prize_eligibility_reason` 仅按当前身份及奖项类型计算，管理员参与同样；没有适合奖项时阻止新报名，已报名者重试仍幂等。此公开资格与个人风险/排除无关，普通响应不会因被关联而变化。旧业务版本不增加奖项报名限制，仍只在开奖时对注册资格筛选未注册者。
- 中奖公示使用可点击的 @昵称，无昵称则 @用户名，链接到该 TG 身份；不出现 Emby 账号名、密码或私密说明。新结果公告列出全部中奖者，不固定人数或省略尾部；按解析 HTML 后的正文 UTF-16 长度（含标题/换行，不计标签/链接原文）限制在每条 4096 内，按完整中奖者行分条，每页保留结果按钮。旧已发送/冻结公告不自动改写或补页。
- 完整公告分页复用 `lottery_notices`，内部唯一 kind 为 `result`、`result:2`…，在开奖事务内一次性冻结；每页独立保存 message_id/状态/重试。前页未确认送达时后页暂停，但不会占满维护批次阻塞其他活动；成功页不重发，failed/unknown 仍走原管理员恢复流程（已知消息优先编辑，unknown 无确认不重试）。管理员详情各页 `kind=result`，多页时附 `page/pages`，按各自 id 恢复；不重抽/重发奖。
- 群消息与中奖私信统一使用三套原生表情包（替代字符与表情包元数据一致，见 `EMOJI` / `DIGITS`）：发起公告为「礼盒 + 标题」行、每个奖项一行彩色礼盒、截止/开奖方式、参与条件、报名费与不退款说明（仅收费；历史公告的公平声明保留）；提醒为沙漏死神 + 截止时间与当时人数；开奖公告为礼炮标题 + 每位中奖者一行皇冠；取消通知为警告标题；中奖私信为礼炮 + 奖品与活动名。各段之间空一行。表情被 Telegram 明确拒绝时仍只降级一次为普通 emoji。
- 中奖私信（升级后发布的活动）：开奖事务内为每位中奖者持久化一条私信任务，内容只有活动名、奖品名和「查看结果 / 领取」按钮（原深链 `startapp=lottery_<id>`），使用抽奖原生自定义表情；私密领取说明不进私信。私信不影响中奖结果和发奖。
- 截止前提醒（开关开启且设有截止时间时）：截止前约 1 小时回复原发起公告发一条简短提醒（带当时报名人数和参加按钮）；发布时距截止不足 90 分钟不发，维护循环错过窗口（剩余不足 10 分钟）跳过，已取消/截止/开奖不发，每期最多一次。
- 发起公告实时人数（升级后发布的活动）：编辑原发起公告，把状态接在**标题行**后面（置顶栏只显示这一行），N 用彩色数字表情，为公开报名总数（与普通端一致）；人数变化才编辑，同一活动至少间隔 30 秒；截止时为「报名截止 · N 人」，开奖后为「已开奖 · N 人参与」，取消时为「已取消」。只针对已确认 message_id 的发起公告；正文其余部分不变。
- 静默置顶（开关开启时）：发起公告确认发送后 `pinChatMessage(disable_notification=true)`，开奖或取消后按 message_id `unpinChatMessage`。Bot 自己置顶所产生的「置顶了消息」服务消息，若 Bot 有删除权限则顺手删除，否则保留。

注册资格沿用 `allow_admin_grant` 与 Bot 原有注册开关、总人数等限制；关闭时保留中奖记录，恢复后可重试。`RegistrationService.resolve/consume` 理解独立 `lottery_admissions` 凭证：resolve 不消费，成功开户后的原同一事务才消费，失败回滚保留资格，重启后也不会复用已消费资格。旧赠送、普通授权、邀请码、卡密流程不变；显式抽奖链接只选择该份本人资格。若开奖后、发资格前已通过其他途径注册，显示需管理员处理，不将该资格转赠/换成邀请码，也不重抽。

## 严格关联排除与部署信任边界

- 新建/复制活动仅按**相同可信公网 IP 摘要 OR 相同浏览器安装随机标识摘要**关联不同 TG，不使用硬件环境、型号、Canvas/WebGL 等摘要判定，也不生成环境「疑似关联」列表；历史已开启环境校验的活动保留原冻结规则（见下节），不追溯改结果。发现重复特征时，同特征的**所有报名账号（包括最先报名者）均排除本场全部奖项**，并保留报名与关联证据；并非只拒绝后来的账号。关联链可在管理端汇总为一个簇。
- **规则可见性**：活动接口的 `rules` 对所有人（含管理员）只含公开规则；严格防小号说明只放在管理员响应的 `admin_rules`（简述为「关联账号全部不中奖（含先报名者），管理员可在报名记录页查看关联原因」），普通响应没有此字段。新建/复制活动的参与页公开规则、发布预览和群公告不出现多账号/防小号/关联/IP/浏览器/设备等检测提示；旧活动仍按原公开规则版本显示，旧环境校验的同意说明也保留。
- 稳定 TG ID 是主体，同 TG 重试不更新信号、不添加名额、不触发自身关联，也不能借换标识解除排除。报名插入、关联识别及资格更新在同一个 `BEGIN IMMEDIATE` 事务中；开奖持有相同数据库写锁，只从 `excluded=0` 的最新报名集合抽取。关闭报名/已开奖后的新请求不写信号，不追溯污染结果。领取、注册资格流程仅消费已经确定的中奖记录，不能绕过排除。历史环境关联的区别是：报名事务只落摘要，是否排除在**开奖事务内**按本期报名判定后并入 `excluded`。
- IP/浏览器规则不使用 UA、设备型号、时区等普通特征。共享出口 IP 会误伤；浏览器标识只是 `crypto.getRandomValues` 生成的 256 位随机值，保存在该 Mini App 同源 `localStorage`，不是硬件 ID、不可伪造凭证或“同一人证明”。不同 Telegram WebView、清缓存、更换浏览器/设备/IP，或主动伪造标识可能绕过检测。除下节仅为兼容历史活动保留、经用户逐场同意的环境校验外，没有外部追踪或全站认证改造；这些限制在管理员编辑/规则页如实说明。普通端仅有统一的校验数据隐私说明（设备校验活动另有同意说明），不显示个体风险判断。
- 浏览器安装标识缺失或格式无效时仍拒绝报名、回滚扣费及报名写入；普通端仅提示「报名暂不可用，请关闭后重新打开活动，或稍后再试」，不展示本地存储等技术原因。已报名者的幂等回执不变。
- 标识通过 HTTPS、已验签 initData 的报名请求提交；服务端只持久化 `HMAC-SHA256(key, [version, activity_id, kind, canonical_value])`，按活动和特征类型域隔离。不存原始 IP/浏览器标识、不记录请求体/这些头，不向任何 API 返回摘要。不启用防刷的活动不落信号。设备摘要的存储方式见下节。

### 历史设备环境校验兼容

环境摘要一致只能说明环境特征相同，不能证明同一物理设备或同一人；不同人的同型号设备也可能碰撞。此能力已从新建/复制活动退役，不降格为「疑似」列表。`app/modules/lottery_device.py` 及客户端 `static/miniapp/ux.js` 仅为服务端已存的旧设备校验活动保留兼容；现有已发布/已开奖记录和排除结果不回算，不退款补抽。

- **配置权威**：新建与复制入口一律保存 `device_check: false`，旧客户端传 true 也不能启用；非布尔值仍拒绝保存。编辑存量草稿时，在同一写事务及 revision 检查中读取该草稿的已存值，保留 true/false（缺字段按 false），不接受客户端 legacy 标记或 `device_check` 值改变它。发布使用服务端已存配置，不以新建默认值覆盖旧策略；只有 `anti_multi` 与已存 `device_check` 同为 true 时执行旧流程。严格模式草稿开关仍按原规则可编辑，发布后全部冻结。普通端不返回开关本身。
- **同意**：`device_check=true` 时详情响应（所有人）带 `consent = {version, title, body, accept, decline}`，当前版本 1，标题「设备校验」，按钮「同意并报名」「不同意」。报名请求必须带整数 `consent_version`（等于当前版本）和客户端数据 `ctx`：缺少或版本不符返回「需同意设备校验后才能参加」；`ctx` 缺失、无法解析或有效项不足返回「未能完成设备校验，请重试」。两者都在同一事务、扣费之前拒绝，不扣费、不写任何记录；未同意时服务端不解码 `ctx`。同意时间与版本随报名存入 `lottery_device_entries`。已报名者的重复请求仍是原幂等回执。关闭设备校验的活动忽略这两个字段，行为不变、不采集。
- **采集**：页面只在用户点「同意并报名」后调用 `window.__mdx.collect()`；加载时不读取任何信息。实现基于 vendored ThumbmarkJS 1.12.0（MIT，来源、校验和与联网审查见 `static/miniapp/vendor/README.md`），关闭其遥测与 beacon、不配置 API key，采集过程无网络请求、无日志。只取与具体 Telegram 客户端无关的项：canvas、WebGL 厂商|渲染器、其余 WebGL、audio、fonts（渲染类在客户端先做 SHA-256）、屏幕「长边x短边x色深x像素比」、CPU 核数、设备内存、触点数、时区；不取语言、UA、plugins、permissions、视口和 `Telegram.WebApp` 字段。`ctx` 另携带浏览器安装标识 `k`（localStorage `md.ux.k`，旧键 `mediadeck.lottery.browser.v1` 迁移后删除），设备校验活动的浏览器规则使用它。
- **存储**：服务端把有效项规范化后只计算 HMAC（沿用 `lottery_identity_key`）：只有活动域 `[lottery-identity-v1, 活动ID, hardware, 规范值]`，只在本期内比对，不同活动之间无法相互关联。原值和 `ctx` 不落库、不记日志，摘要不由任何 API 返回。
- **判定**：每期单独判定、从第一场起立即生效，不依赖其他活动或历史基线。本期内环境摘要相同的账号按该历史活动原规则全部排除（包括先报名者），不将此事实称为同一设备或同一人。
- **iPhone / iPad 不做设备判定**：同型号同系统的 iPhone 采集值几乎相同，无法区分。服务端按采集值识别 iOS/iPadOS WebKit（显卡为 Apple、有触点、无 deviceMemory），这类报名不保存设备摘要，因此既不排除也不提示；同 IP、同浏览器标识规则照常适用。同意弹层对所有人一致。
- **生效时点**：报名期间管理端看到实时判定；**最终以开奖事务内的判定为准**——在读取候选人之前计算，写入 `verdict` 并合并到 `lottery_entries.excluded`。开奖后展示冻结结果。
- **展示**：管理端历史关联原因显示「设备环境特征相同」，与 IP/浏览器关联可汇总为一个簇；设备校验说明只放在管理员的 `admin_rules`。同意弹层文案只说明读取的信息与「本期活动的参与资格校验」用途，不提多账号。普通端报名与结果响应与其他人完全一致，不含判定信息，群公告不出现。
- **局限**：同型号、同系统版本且设置相同的不同手机可能得到相同摘要而被一起排除（立即生效、不做常见配置豁免，误判由管理员在记录页核查）；系统/驱动升级、安装字体、修改时区会改变摘要；更换设备、虚拟机或主动伪造可以绕过。这是辅助信号，不是“同一人证明”。

### 可信 IP 配置（部署人员必须明确确认）

环境变量 **`MEDIADECK_LOTTERY_IP_MODE=cloudflare_protected`** 才启用 Cloudflare 来源。默认 `disabled`，未知值也安全关闭。此值是**运营者对整个回源边界的显式信任声明**，不是根据某个请求头自称来自 Cloudflare：

1. 先确认 Mini App 仅通过受控 Cloudflare edge/Tunnel 访问，origin 没有可绕过 Cloudflare 的公网/其他代理路径；隧道配置不能由非可信主体改写，本机回源端口也不供不可信调用者使用。Cloudflare 必须覆盖 `CF-Connecting-IP`；如使用 Workers、自定义 Transform/Pseudo IPv4 等会改写来源的设置，应先确认其不会让客户端选择该值，或会把多个真实访客折成同一值。不能满足此边界就**不要开启**该模式。
2. 开启后仅读取唯一的 `CF-Connecting-IP`，拒绝重复头、多值、带端口/zone、无效和非公网 IP；IPv4-mapped IPv6 归一化后再摘要。完全忽略客户端 body 的 IP、XFF、Forwarded、X-Real-IP，以及 `request.client`。
3. Uvicorn 可能在应用之前根据默认代理规则改写 `scope.client`，因此不能用它是否 loopback 二次猜测代理信任，更不能把 loopback 当所有人的 IP。此功能**不改全站 Uvicorn 代理行为或登录限速**。未配置来源、无可信公网 IP 或浏览器本地存储不可用时，严格模式不接受新报名，普通端给通用「报名暂不可用」提示；不会静默降级，也不会将全员误判一簇。管理编辑页会提示配置是否启用；它不能替代部署人员的网络边界核实。
4. 部署后先在授权测试活动用两个独立网络/浏览器正常报名，再用相同网络或同浏览器的两个 TG 验证管理端全部排除和普通端静默状态；不得以伪造头的公网调用代替真实链路验收。不要记录/公开实际用户 IP 或设备标识。

### HMAC 密钥持久性

首次有效严格报名在数据库事务中用 `secrets.token_hex(32)` 生成唯一服务端密钥，持久化于 `lottery_identity_key(id=1)`，所有 worker/重启共用；无外部环境密钥依赖。必须保护数据库及备份读取权限，并把该表与 `lottery_signals`、报名/活动表**一致备份和恢复**。已有信号而密钥缺失或损坏时拒绝新报名，不自动换钥。设备校验的 `lottery_device_entries` 同样依赖此密钥，须与上述表一起一致备份恢复；该表有数据而密钥缺失时，所有严格活动同样拒绝新报名。不要删除、手动轮换、独立恢复该表或把新随机密钥当修复，否则后续关联会失效；应恢复对应原密钥并核查完整性。开奖只使用已落库资格，缺失来源不改变已经确定的结果。

## 状态与失败恢复

三件事彼此独立：`lotteries.state=settled` 表示抽样结果已确定；`lottery_awards.state=delivered` 表示对应奖励已入账/入包或资格已授予（不等于已使用）；`lottery_notices.state=sent` 才表示 Telegram 已确认公告。网络异常不撤销结果、不重新抽奖。

- 维护循环触发单个受 lifecycle 管理的后台任务；慢 Telegram 请求不会阻塞原会员维护。停止进程时任务先取消并收尾，再关闭数据库。无第二套服务/polling/Cron。关闭 Bot 时拒绝新报名、暂停公告发送并保留待发状态；已到期活动仍可结算，恢复 Bot 后再送达公告。
- 自动奖励失败：奖励行保留 `failed`，五分钟后重试；管理员可点「重试未发奖励」，中奖者也可主动领取。先检查注册通道/分组、数据库服务状态，不要手动把行改回待抽或自行补积分。
- 已明确被 Telegram 拒绝：公告显示 `failed`。修复 Bot/群/话题权限或配置后，在活动内「核验 / 恢复公告」。发布配置冻结；目标话题错误时不要绕过数据库冻结改群或改奖池。
- 明确自定义 emoji 无效、不支持或权限拒绝：仅该抽奖请求移除原生自定义表情/按钮图标后安全重试一次。其他 Bot 场景不变。
- 明确连接失败（非 timeout）或限流：持久化指数退避，自动尝试总计最多四轮。限流遵守 `retry_after`；达到上限显示失败，等待管理员处理。
- **任何 timeout、5xx、未确认结果**：记为 `unknown`，禁止自动重新发送。进程在 `sending` 中断，三分钟后也转为 `unknown`。管理员须检查目标群/话题：已有公告时填写原消息 ID，优先 `editMessageText`；确认原公告不存在时勾选人工核验后才可重新发送。这是显式授权恢复，不是保证网络恰好一次。
- 已知消息 ID 的编辑返回「内容未变化」视为成功。未取得确认的消息无法用 Telegram Bot API 按任意聊天历史检索，不能假装已验证不存在；核验是管理员责任。
- 结果深链是原活动深链，可反复打开查看最新派奖状态；不在公开结果中展示个人绑定状态或私密领取说明。
- **新增的群消息 / 私信 / 编辑 / 置顶**（提醒与取消通知走 `lottery_notices`；中奖私信走 `lottery_dms`；置顶、取消置顶、人数编辑走 `lottery_ops`）沿用同一语义：timeout、5xx、未确认结果记 `unknown` 且不自动重发（同一编辑内容不重复提交；`sending` 中断超过三分钟转 `unknown`）；明确拒绝如实记录 `failed`；明确连接失败或限流按退避最多四轮；Bot 关闭时暂停并保留。私信遇 403（未私聊过 Bot、已屏蔽、已注销）或「chat not found」记为 `unreachable`（无法私信），不重试、不影响其他人。置顶/编辑无权限只记录给管理员，不重试刷屏。这些操作都不会改变报名、开奖结果或发奖。
- 被取消活动的发起公告若尚未发送成功，不再补发，也不发取消通知（群里未见过该活动）。

## Migration / rollback

启动通过 `Database._migrate` 增加 `lotteries`、`lottery_entries`、`lottery_awards`、`lottery_admissions`、`lottery_notices`、`lottery_signals`、`lottery_identity_key` 七张独立表及索引，设备校验另由 `lottery_device.migrate` 增加 `lottery_device_entries` 表（只建表、不回填）；报名表增加 `excluded`，不重写旧会员/积分/邀请码数据。旧抽奖配置缺少 `anti_multi` 时，草稿迁移为默认开启，已发布/已结束活动保持关闭，避免追溯修改冻结规则；新期默认严格。本次环境校验退役无需新增或破坏性迁移，不批量回写旧配置，不清除历史摘要、排除、中奖、积分或公告记录。上线前按现有流程做一致性 SQLite 备份（包含 WAL 一致状态），在副本验证 migration。

回滚代码到不支持抽奖的版本会停止抽奖任务，原版本也不理解抽奖注册凭证。**不要删除新表、重置活动或恢复过时备份来“重试”**：已发的积分、背包和邀请名额属于现有权威表，盲目倒退会破坏账本、重发奖励或重新开放已消费凭证。应先核查未开奖活动、未领/未发奖励和未知公告；必要时保留支持抽奖的维护窗口处理，再走批准的回滚流程。新表可保留给后续恢复升级，旧代码不消费它们。尤其不能回滚到能开奖却不理解 `excluded` 的中间版本来处理严格活动，否则会让已排除账号参与中奖；所有仍开放的严格活动应由支持本规则的版本完成。HMAC 表与关联记录不能分离回滚。同理，存在仍开放的设备校验活动时，不得回滚到不理解 `device_check` 的后端，否则会在未同意、未采集的情况下接受报名，开奖也不会合并设备排除。

运营功能（v0.50.0 之后）只做增量迁移：新表 `lottery_dms`（中奖私信任务，`award_id` 唯一）、`lottery_ops`（置顶 / 取消置顶 / 人数编辑，主键 `(lottery_id, kind)`）及其索引，`lotteries` 增加可空列 `cancelled_at`；不回填、不改写旧活动配置。新配置字段 `min_level`、`min_points`、`min_watch_hours`、`reminder`、`pin`、`winner_dm`、`live_count` 在旧活动中缺失时一律按「不限 / 关闭」读取。回滚到旧版本时，旧代码不理解 `cancelled` 状态（按「未发布」拒绝报名与开奖）也不处理新表，已退积分保留在账本；存在设有门槛的开放活动时不得回滚到忽略门槛的旧后端。

收费能力无需新表或迁移。**存在仍开放的收费活动时，不得回滚到忽略 `entry_fee` 的旧后端**，否则会错误允许免费报名；优先前向修复，或在批准的维护安排下先妥善结束开放活动。不可通过回滚数据库撤销已扣积分或重建报名。
