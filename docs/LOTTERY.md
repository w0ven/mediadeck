# Mini App 群抽奖

抽奖使用现有 `/app` 与 `/api/app/lottery/*`，不另开后台域名、不新增 Bot polling 或 Cron。已批准的 Lucky Studio 视觉已接入正式页面：蓝紫光斑、渐变按钮、毛玻璃、原始彩色 LUCKY 字母和礼物素材；没有演示身份、演示名单或固定中奖结果。

## 配置与入口

1. 保留 [MINIAPP.md](MINIAPP.md) 的 HTTPS 与反向代理边界，只公开 `/app`、`/app/*`、`/api/app/*`；不要公开管理后台路由。
2. 配置并启用 Bot、会员面板地址和「群互动白名单」。把 Bot 加入目标群并设为管理员，确保 `getChatMember` 能可靠检查其他用户；禁止发言等群权限仍需正确配置。
3. 在 **BotFather → Bot Settings → Configure Mini App → Enable Main Mini App**（客户端文案可能不同）设置该 Bot 的主 Mini App，地址与配置的会员面板地址对应。群里不能使用 `web_app` 按钮，本功能使用普通 URL：`https://t.me/<当前Bot用户名>?startapp=lottery_<活动ID>`。代码只从 `getMe` 获取用户名，不猜 short_name；发布时要求 `has_main_web_app=true`，否则拒绝发布。仅配置私聊 Web App 按钮不等于配置了 Main Mini App。
4. 管理员是**已绑定账号的现有 admin 角色**，通过 Telegram initData 验签后查库认定，不信任 URL、前端角色或客户端传入 uid。管理员会员首页显示「抽奖管理」；普通会员不显示该入口，未注册用户也无权访问管理 API。
5. 抽奖正文使用 Telegram 原生 `<tg-emoji emoji-id="…">…</tg-emoji>`，按钮使用 `icon_custom_emoji_id`。Bot 所有者需具备 Telegram 要求的 Premium 条件。素材来自指定的 Colorful Font、ZaiHuaNews、Mix Emoji，来源见静态素材目录的 `SOURCES.md`。本功能不会改动其他 Bot 文案/按钮。

## 管理员操作

- 管理员从群深链进入时与群友一样报名和领奖，额外有「管理本期」入口；从个人页「抽奖管理」进入活动则默认管理视图，可返回参与页。管理员不豁免报名条件、积分费用或风控。
- 抽奖管理 → 新建：填写标题、白名单群、可选话题 ID、参与对象、报名费用、开奖方式、北京时间截止时间，并添加奖项。话题 ID 仅用于论坛群；应由管理员确认目标话题实际存在且可发言。
- 草稿可编辑（奖项可移除/重新添加）。保存时服务器验证对象、商品、分组、奖项数量与天数；同一草稿的并发编辑有 revision 冲突保护。
- 「发布前预览」只展示正文，不发送消息。确认发布后进行 Bot/主 Mini App/群身份检查，再冻结全部活动配置并持久化发起公告。发布结果中应查看**公告状态**，不能只看到活动是「报名中」就认为群消息已成功。
- 每期支持 1–20 个奖项、最多 200 个获奖名额；每项 1–200 名。积分每人 1–100000、可用邀请名额每人 1–100；注册资格有效天数 1–3650。截止时间须为保存/发布检查时至少一分钟之后、最多 366 天之后。
- 每期默认开启「严格防小号」，草稿可关闭；发布后连同奖池、参与对象、群/话题、人数、时间全部冻结，不提供临开奖放行或重抽。手动开奖可提前停止报名，需再次确认；定时开奖在截止后的现有 lifecycle 维护周期执行（默认周期 15 秒，繁忙时可能延后）。截止边界由服务器硬性判断，不依赖浏览器时间。
- 每期详情显示报名总数、异常排除人数和当前候选人数；「报名记录 / 关联异常账号」分页查看报名及结果，并查看关联簇的昵称、必要 TG ID、直接关联原因（IP / 浏览器标识）、关联时间和排除结果。关联证据不返回 IP/设备原值或摘要。只有后端确认的管理员可以访问这些数据，普通端无法通过伪造角色获得。
- 已开奖页显示真实中奖名单、每份奖励的状态、发起/结果两条公告的独立状态。人工奖品实际交付后再点「确认已人工发放」。发放记录与管理员操作进入 `audit_log`。

## 群友参与与领奖

- 从群按钮直达对应活动。initData 必须由 Telegram 签名，但不要求先注册/绑定。无活动深链的未绑定用户只看到欢迎/指引，不会取得会员私有数据；原会员 API 仍要求绑定。
- 报名时必须属于发布群，且符合全部/仅已注册/仅未注册的条件。查询失败、已离群或受限且非成员时拒绝报名；不会把查询失败当作已入群。
- 报名费用 `entry_fee` 为 0–100000 整数，0 免费；旧活动缺失该字段时仍免费，不回写旧配置或补扣。收费活动要求已绑定积分账户，不能选「仅未注册」或配置本人注册资格奖。选择「全部群友」的收费活动同样要求积分账户。
- 收费按钮展示金额，确认后才提交 `expected_entry_fee`；后端要求与冻结费用相同，旧客户端未确认费用时拒绝收费。公告和页面明确成功报名后不退，未中奖或关联排除也不退款。报名失败不扣费。
- 扣积分、报名与关联记录在同一事务完成；账本理由 `lottery.entry`，引用 `lottery.entry:<活动ID>:<TG ID>`。数据库唯一键保证每个 TG 每期仅一次，重复或并发请求不重复扣费、不增加名额。到达截止时刻即停止报名；已经报名者可刷新活动查看结果。
- 所有已接受的报名统一显示「报名已记录 / 等待开奖」。风控静默执行，普通响应不包含本人风险、排除、关联簇或有效候选人数；普通总报名数包含异常报名。结果页按真实结果正常显示未中奖，不伪造获奖或奖励发放。异常名单不会进入群公示。
- 奖项使用 `secrets.SystemRandom` 无偏抽样。**先抽本人注册资格，再抽其他奖项**；两个类别内奖项随机排序，每个名额在剩余合资格报名者中等概率抽取。每人最多一奖；人数不足如实少发，不补抽。
- 报名对象按报名当时账号状态判断；**注册资格另外在开奖事务中再次排除已经注册者**，混合奖池也遵循此规则。以上规则在活动页公开说明。
- 中奖公示使用可点击的 @昵称，无昵称则 @用户名，链接到该 TG 身份；不出现 Emby 账号名、密码或私密说明。群公告仅保留必要信息，最多展示前 12 位并链接完整名单；旧已发送/冻结公告不自动改写。

| 奖励 | 实际发放与领取 |
| --- | --- |
| 商城道具 | 读取当前启用商品，草稿保存时冻结规格快照（发布时再次检查商品仍有效）。中奖后调用 `InventoryService.add` 同事务入包，不扣积分、不占商城购买次数；使用后才生效，沿用原道具上限与权益同步。支持 invite / bandwidth / streams / title / whitelist card。 |
| 商城自定义商品 | 完整规格及私密购买后说明进背包，沿用保留天数与本人查看规则；私密内容不进群公示。 |
| 积分 | 使用原 `points_ledger` 事务记账，理由 `lottery.award`，余额直接增加。 |
| 可用邀请名额 | 增加 `members.invite_quota`，可通过原邀请流程生成邀请码；不是历史成功邀请人数，也不是本人注册资格。 |
| 自定义人工奖品 | 公开名称；领取说明仅中奖者和管理员可见。管理员实际交付后确认，确认幂等。 |
| 本人专属注册资格 | 独立持久凭证，绑定中奖 TG、奖项分组及天数；不可转赠，不改写已有 admin grant/赠送资格。获奖者点「进入 Bot 注册」走原用户名 → 密码方式选择 → 最终确认流程，不自动创建账号/替用户设置密码。 |

未注册中奖者的积分、邀请名额、商城奖励会保留为「待绑定领取」。绑定后可回到原结果深链点「刷新绑定并领取奖励」；后台也每隔约五分钟重试待绑定奖励。发放与状态更新同事务，反复领取、响应丢失、重启、并发不会重复入账/入包。

注册资格沿用 `allow_admin_grant` 与 Bot 原有注册开关、总人数等限制；关闭时保留中奖记录，恢复后可重试。`RegistrationService.resolve/consume` 理解独立 `lottery_admissions` 凭证：resolve 不消费，成功开户后的原同一事务才消费，失败回滚保留资格，重启后也不会复用已消费资格。旧赠送、普通授权、邀请码、卡密流程不变；显式抽奖链接只选择该份本人资格。若开奖后、发资格前已通过其他途径注册，显示需管理员处理，不将该资格转赠/换成邀请码，也不重抽。

## 严格关联排除与部署信任边界

- 每期按**相同可信公网 IP 摘要 OR 相同浏览器安装标识摘要**关联不同 TG。发现重复特征时，同特征的**所有报名账号（包括最先报名者）均排除本场全部奖项**，并保留报名与关联证据；并非只拒绝后来的账号。关联链可在管理端汇总为一个簇。
- 稳定 TG ID 是主体，同 TG 重试不更新信号、不添加名额、不触发自身关联，也不能借换标识解除排除。报名插入、关联识别及资格更新在同一个 `BEGIN IMMEDIATE` 事务中；开奖持有相同数据库写锁，只从 `excluded=0` 的最新报名集合抽取。关闭报名/已开奖后的新请求不写信号，不追溯污染结果。领取、注册资格流程仅消费已经确定的中奖记录，不能绕过排除。
- 不使用 UA、设备型号、时区等普通特征判定同人。共享出口 IP 会误伤；浏览器标识只是 `crypto.getRandomValues` 生成的 256 位随机值，保存在该 Mini App 同源 `localStorage`，不是硬件 ID、不可伪造凭证或“同一人证明”。不同 Telegram WebView、清缓存、更换浏览器/设备/IP，或主动伪造标识可能绕过检测。没有引入第三方指纹库、外部追踪或全站认证改造；这些限制在管理员编辑/规则页如实说明。普通端仅有统一的校验数据隐私说明，不显示个体风险判断。
- 标识通过 HTTPS、已验签 initData 的报名请求提交；服务端只持久化 `HMAC-SHA256(key, [version, activity_id, kind, canonical_value])`，按活动和特征类型域隔离。不存原始 IP/浏览器标识、不记录请求体/这些头，不向任何 API 返回摘要。不启用防刷的活动不落信号。

### 可信 IP 配置（部署人员必须明确确认）

环境变量 **`MEDIADECK_LOTTERY_IP_MODE=cloudflare_protected`** 才启用 Cloudflare 来源。默认 `disabled`，未知值也安全关闭。此值是**运营者对整个回源边界的显式信任声明**，不是根据某个请求头自称来自 Cloudflare：

1. 先确认 Mini App 仅通过受控 Cloudflare edge/Tunnel 访问，origin 没有可绕过 Cloudflare 的公网/其他代理路径；隧道配置不能由非可信主体改写，本机回源端口也不供不可信调用者使用。Cloudflare 必须覆盖 `CF-Connecting-IP`；如使用 Workers、自定义 Transform/Pseudo IPv4 等会改写来源的设置，应先确认其不会让客户端选择该值，或会把多个真实访客折成同一值。不能满足此边界就**不要开启**该模式。
2. 开启后仅读取唯一的 `CF-Connecting-IP`，拒绝重复头、多值、带端口/zone、无效和非公网 IP；IPv4-mapped IPv6 归一化后再摘要。完全忽略客户端 body 的 IP、XFF、Forwarded、X-Real-IP，以及 `request.client`。
3. Uvicorn 可能在应用之前根据默认代理规则改写 `scope.client`，因此不能用它是否 loopback 二次猜测代理信任，更不能把 loopback 当所有人的 IP。此功能**不改全站 Uvicorn 代理行为或登录限速**。未配置来源、无可信公网 IP 或浏览器本地存储不可用时，严格模式不接受新报名，普通端给通用「报名暂不可用」提示；不会静默降级，也不会将全员误判一簇。管理编辑页会提示配置是否启用；它不能替代部署人员的网络边界核实。
4. 部署后先在授权测试活动用两个独立网络/浏览器正常报名，再用相同网络或同浏览器的两个 TG 验证管理端全部排除和普通端静默状态；不得以伪造头的公网调用代替真实链路验收。不要记录/公开实际用户 IP 或设备标识。

### HMAC 密钥持久性

首次有效严格报名在数据库事务中用 `secrets.token_hex(32)` 生成唯一服务端密钥，持久化于 `lottery_identity_key(id=1)`，所有 worker/重启共用；无外部环境密钥依赖。必须保护数据库及备份读取权限，并把该表与 `lottery_signals`、报名/活动表**一致备份和恢复**。已有信号而密钥缺失或损坏时拒绝新报名，不自动换钥。不要删除、手动轮换、独立恢复该表或把新随机密钥当修复，否则后续关联会失效；应恢复对应原密钥并核查完整性。开奖只使用已落库资格，缺失来源不改变已经确定的结果。

## 状态与失败恢复

三件事彼此独立：`lotteries.state=settled` 表示抽样结果已确定；`lottery_awards.state=delivered` 表示对应奖励已入账/入包或资格已授予（不等于已使用）；`lottery_notices.state=sent` 才表示 Telegram 已确认公告。网络异常不撤销结果、不重新抽奖。

- 维护循环触发单个受 lifecycle 管理的后台任务；慢 Telegram 请求不会阻塞原会员维护。停止进程时任务先取消并收尾，再关闭数据库。无第二套服务/polling/Cron。关闭 Bot 时拒绝新报名、暂停公告发送并保留待发状态；已到期活动仍可结算，恢复 Bot 后再送达公告。
- 自动奖励失败：奖励行保留 `failed`，五分钟后重试；管理员可点「重试未发奖励」，中奖者也可主动领取。先检查注册通道/分组、数据库服务状态，不要手动把行改回待抽或自行补积分。
- 已明确被 Telegram 拒绝：公告显示 `failed`。修复 Bot/群/话题权限或配置后，在活动内「核验 / 恢复公告」。发布配置冻结；目标话题错误时不要绕过数据库冻结改群或改奖池。
- 明确自定义 emoji 无效、不支持或权限拒绝：仅该抽奖请求移除原生自定义表情/按钮图标后安全重试一次。其他 Bot 场景不变。
- 明确连接失败（非 timeout）或限流：持久化指数退避，自动尝试总计最多四轮。限流遵守 `retry_after`；达到上限显示失败，等待管理员处理。
- **任何 timeout、5xx、未确认结果**：记为 `unknown`，禁止自动重新发送。进程在 `sending` 中断，三分钟后也转为 `unknown`。管理员须检查目标群/话题：已有公告时填写原消息 ID，优先 `editMessageText`；确认原公告不存在时勾选人工核验后才可重新发送。这是显式授权恢复，不是保证网络恰好一次。
- 已知消息 ID 的编辑返回「内容未变化」视为成功。未取得确认的消息无法用 Telegram Bot API 按任意聊天历史检索，不能假装已验证不存在；核验是管理员责任。
- 结果深链是原活动深链，可反复打开查看最新派奖状态；不在公开结果中展示个人绑定状态或私密领取说明。

## Migration / rollback

启动通过 `Database._migrate` 增加 `lotteries`、`lottery_entries`、`lottery_awards`、`lottery_admissions`、`lottery_notices`、`lottery_signals`、`lottery_identity_key` 七张独立表及索引；报名表增加 `excluded`，不重写旧会员/积分/邀请码数据。旧抽奖配置缺少 `anti_multi` 时，草稿迁移为默认开启，已发布/已结束活动保持关闭，避免追溯修改冻结规则；新期默认严格。上线前按现有流程做一致性 SQLite 备份（包含 WAL 一致状态），在副本验证 migration。

回滚代码到不支持抽奖的版本会停止抽奖任务，原版本也不理解抽奖注册凭证。**不要删除新表、重置活动或恢复过时备份来“重试”**：已发的积分、背包和邀请名额属于现有权威表，盲目倒退会破坏账本、重发奖励或重新开放已消费凭证。应先核查未开奖活动、未领/未发奖励和未知公告；必要时保留支持抽奖的维护窗口处理，再走批准的回滚流程。新表可保留给后续恢复升级，旧代码不消费它们。尤其不能回滚到能开奖却不理解 `excluded` 的中间版本来处理严格活动，否则会让已排除账号参与中奖；所有仍开放的严格活动应由支持本规则的版本完成。HMAC 表与关联记录不能分离回滚。

收费能力无需新表或迁移。**存在仍开放的收费活动时，不得回滚到忽略 `entry_fee` 的旧后端**，否则会错误允许免费报名；优先前向修复，或在批准的维护安排下先妥善结束开放活动。不可通过回滚数据库撤销已扣积分或重建报名。

## 本地验证与真实环境验收
